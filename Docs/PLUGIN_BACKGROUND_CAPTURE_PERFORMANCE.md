# AviUtl2プラグインの背景取得による再生・シーク遅延と対策

記録日: 2026-09-20。MapRakuプラグインの実機調査を基に、同様の背景取得処理を持つ他のプラグインへ適用するための資料。

## 結論

編集画面に表示する参照背景の色変換を、映像コールバックで毎フレーム実行しない。再生中は背景を元の画素形式で保存し、編集画面が背景を要求した時にRGBA8へ変換する。

背景が映像出力そのものに必要なプラグインには、この遅延変換をそのまま適用しない。まず背景の利用箇所を確認する。

## 発生した現象と実測

道2本・ルート2本の簡単な地図でも、AviUtl2の再生・シークが重かった。静的な地図やルートのキャッシュを改善しても、体感の改善が小さかった。

1920×1080の同じ地図で、初回のキャッシュ生成を除く実機ログを比較した。

| 計測対象 | 変更前 | 変更後 |
|---|---:|---:|
| 編集画面用の背景取得・保存（変更前は色変換を含む） | 約109〜114ms | 約4.9〜5.5ms |
| 地図描画・表示位置調整・映像出力 | 約15〜19ms | 約16〜17ms |
| プラグイン処理全体 | 約125〜130ms | 約21〜23ms |

代表ログの値は、変更前が `capture=113.259 process=128.703`、変更後が `capture=5.148 process=22.570`（単位ms）。ユーザーも軽くなったことを確認した。

これは当該環境での計測値であり、他のプラグインの改善幅やAviUtl2全体のフレームレートを保証するものではない。ログは背景取得の合計を測っており、GPU待機と色変換を個別計測した値ではない。ただし、色変換の実行タイミングを変更したことで背景取得時間が大幅に短縮した。

## 原因

変更前の処理は次の順序だった。

```text
映像コールバック（毎フレーム）
  → 設定データ更新
  → 編集画面用背景の取得
      → GetFramebufferTexture2D
      → GPUのステージングテクスチャへCopyResource
      → MapでCPUから参照可能にする
      → 全画素をRGBA8へ変換して保存
      → Unmap
  → 地図・マーカー描画
  → 入力映像への合成・出力
```

編集画面を開いていない時も、参照背景の全画素変換を繰り返していた。1920×1080では約207万画素あり、地図のオブジェクト数が少なくても処理量は減らない。

元画像の形式に応じて、BGRAの並べ替えや16bit成分の8bit化が必要になる。特にFLOAT16の場合は各画素の各成分について半精度浮動小数点の復元、値の制限、8bit化が発生する。GPUからの取得は単純なメモリコピーだけとは限らず、`Map`でGPU処理の完了を待つ可能性もある。

## 最初の計測で見落とした理由

最初のタイマーは `RenderVideo` の中にあり、その直前に `ProcessVideo` が実行する `CaptureBackground` を含んでいなかった。「total」という名前でも、映像コールバック全体の時間ではなかった。

そのため、描画キャッシュが効いていて描画時間が短縮しているのに、再生が重い状態を説明できなかった。疑似ホストで描画だけを測るテストも、実際のGPU背景取得を再現しなければこの負荷を検出できない。

他のプラグインでは、最初に映像コールバックの入口から出口まで測り、内訳との不一致を探す。

## 実装方針

### 毎フレームは元形式のバイト列を保存する

`Capture`ではステージングテクスチャの取得までを維持し、マップした画像を変換せずにCPU側の所有バッファへコピーする。

- 幅・高さ・DXGI形式を画素データと一緒に保持する。
- 1画素のサイズは形式ごとに決める。RGBA8/BGRA8は4バイト、RGBA16は8バイト。
- GPU画像の行間隔には `Mapped.RowPitch` を使う。`Width * BytesPerPixel` と一致するとは限らない。
- 保存先は余分な行パディングを含めず、各行の有効画素だけコピーする。
- マップしたポインターを保存して後で参照しない。`Unmap`前に自分のバッファへコピーする。
- `Unmap`は `finally` で確実に行う。
- デバイス・寸法・形式が変化した時は、ステージングリソースを作り直す。

### 編集画面が必要とする時にRGBA8へ変換する

`CopyRgba`で次の順序を守る。

1. ロックを取得する。
2. 元形式の画素データを独立した配列へコピーし、寸法と形式も取得する。
3. ロックを解放する。
4. コピーしたデータをRGBA8へ変換し、呼び出し側へ返す。

色変換中ずっと背景保存用のロックを保持しない。単なる動的配列の代入で共有するのではなく、独立したスナップショットを作る。再生側の次の書き込みと競合させない。

```text
変更後の再生中:
  GPU背景取得 → 元形式でコピー・保存 → 地図描画・出力

編集画面を開く時:
  保存した背景のスナップショット取得 → RGBA8変換 → 背景表示
```

### 維持すべき動作とトレードオフ

- 背景は毎フレーム保存するため、編集画面で最新の取得済み背景を利用できる。
- 映像出力用の画像と編集用の参照背景を混同しない。
- 色・透明度・クランプ処理は従来の変換と揃える。
- 背景取得失敗時は古い画像を誤表示しないよう、データ・寸法・状態を適切に更新する。
- 色変換の時間は編集画面を開く時へ移るため、その時の待ち時間は残る。
- RGBA16を保持する場合、保存バッファはRGBA8の2倍になる。1920×1080では約16.6MB（従来は約8.3MB）。編集時にはスナップショットと変換結果の追加メモリも必要になる。
- GPUからCPUへの転送・同期は毎フレーム残る。今回の修正はGPU取得自体を要求時だけにしたものではない。

## 他のプラグインでの調査手順

1. `GetFramebufferTexture2D`、`CopyResource`、`D3D11_MAP_READ`、`HalfToSingle`、`CopyRgba`などを検索する。
2. 取得画像が編集画面の参照用か、映像出力にも必要かを呼び出し元まで確認する。
3. 実際のAviUtl2で、少数オブジェクトの再生・シークを計測する。
4. ロック待ち、設定更新、背景取得、描画、入力取得、合成、出力送信を分ける。
5. 背景取得が支配的なら、取得・GPU待機・コピー・変換をさらに分けて測るか、今回のように変換を遅延させて比較する。
6. 同じプロジェクト・解像度・操作・ビルド条件で変更前後を比較する。初回のリソース生成は定常時と分ける。

MapRakuで追加したログ項目:

| 項目 | 意味 |
|---|---|
| `lock_wait` | 描画ロックを取得するまでの待ち時間 |
| `update` | シリアライズ済み設定データの更新時間 |
| `capture` | 編集画面用背景の取得・保存時間 |
| `map` | 地図・軌跡・マーカー描画時間 |
| `viewport` | 表示位置・拡大率・表示枠の処理時間 |
| `input` | 入力バッファ準備とAviUtl2からの入力取得時間 |
| `composite` | 出力画像への合成時間 |
| `submit` | AviUtl2への画像送信時間 |
| `total` | `RenderVideo`内の時間。背景取得は含まない |
| `process` | ロック待ち・設定更新・背景取得・`RenderVideo`の合計 |

`process`もログ書き込みやコールバック外側の処理まで含む厳密なホスト全体の時間ではない。ログは毎フレーム大量出力せず、今回のように約1秒間隔などへ制限する。PID・解像度・ビルド識別情報も残し、テスト実行のログと実機ログを混同しない。ビルド表示に使う条件定義が実際の構成と一致しているかも確認する。

## 検証項目

- RGBA8/BGRA8（sRGB形式を含む）、RGBA16 UNORM/FLOATそれぞれの変換結果。
- 複数行の画素順序、RGBとアルファ、範囲外の値の制限。
- 出力配列を書き換えても元データが変わらないこと。
- 不正な寸法、不足したバッファ、未対応形式の扱い。
- 解像度・形式・GPUデバイス変更時の再作成と、取得失敗時の復帰。
- 再生・シーク後に編集画面を開き、最新の背景・色・透明度が正しいこと。
- 地図などの映像出力が変わっていないこと。
- 疑似ホストのテストに加え、実AviUtl2のログで背景取得を含む全体時間が短縮していること。

実機ログの保存先は `%TEMP%\MapRakuPluginPerformance.log`。今回の対策を他のプラグインへ適用する際は、ファイル名の一括置換ではなく、背景の用途・所有権・スレッド間の受け渡しを確認して移植する。
